Before citing any corpus result as "settled / in hand / forced," grep for its retraction or superseding note FIRST. I (Lyra) re-surfaced retracted results **twice** in the 2026-07-29 fermion-sector arc, both caught by Keeper's reconnect:

1. **K969 vs K945:** declared the generation count "open from scratch" — but K945 already had ≤3 DERIVED via three routes. "Open" is a status-claim too.
2. **F738 vs F669:** cited "e↔μ overlap = c₅/c₃ = Γ(5)/π², in hand (F666)" — but I had **retracted exactly that in F669** (T2511: the {5,3,0} nested geometry is inconsistent, idempotents dim-1; the proved c₅/c₃ = 159/1195 is a λ-rational ≠ Γ(5)/π²).

**Why:** the failure mode is reaching for a corpus result that *fits the tidy story* without checking whether it survived. It's the same corpus-reconnect rule ([[feedback_corpus_reconnection_before_declaring_irreducible]]) I enforce on the whole team — and it binds **hardest on my own prior claims**, because I trust my own memory of them.

**How to apply:** when a note wants to lean on a prior result, `grep -rl` the result ID + "retract/supersede/RETRACTED/walkback" before writing "in hand." An assumed identification (c-function equalities, "maximal" angles like θ₂₃=π/4 when the corpus holds 4/7) is exactly what the blind bar exists to stop — the fix is to build on the *exhibited* object (e.g. F323's localization-overlap integral where π enters from the Bergman measure, not an assumed ratio), never the assumed one.
